# AI 面试题生成链路认知

- 小程序 AI 面试题由服务端实时调用大模型生成，主要入口是 `server/index.ts` 的 `GET /api/candidate/interview-questions`。
- 当前小程序主流程一次性拉取 6 道题，服务端走 `generatePersonalizedInterviewSix()`；分段函数 `generatePersonalizedInterviewFirst()` / `generatePersonalizedInterviewRest()` 也存在，但不是当前小程序主调用路径。
- 生成题目的 `system prompt` 现在走“AI 面试官模板”：预设 `申朴面试官AI` 已落库到业务库 `ai_interview_prompt_templates`，后续模板也在这张表里维护。
- 生成题目的 `user prompt` 模板写死在 `server/index.ts` 的 `buildPersonalizedInterviewUserPromptBlock()` 中，不在数据库。
- `user prompt` 填充值来自数据库：岗位信息从 `jobs` 表读取，简历信息从 `resume_screenings` 表读取。
- `jobId` 对应 `jobs.job_code`，例如 `JMNY2RJ5K` 是岗位编号，用来读取 `jobs.title`、`jobs.department`、`jobs.jd_text`。
- `resumeScreeningId` 对应 `resume_screenings.id`，是后台某条简历筛查记录的主键，用来精准定位候选人简历。
- `resume_screenings` 表记录候选人某次投递/上传简历后的 AI 筛查结果，包括候选人姓名、手机号、岗位编号、简历正文、AI 摘要、匹配分、筛查状态、流程阶段等。
- 后台对应页面主要是 `src/` 里的简历筛查/简历库相关页面；用户在后台看到的一条筛查记录，其 ID 就是后续小程序邀请和 AI 面试出题使用的 `resumeScreeningId`。
- 出题时读取简历优先级：如果传入 `resumeScreeningId`，先用 `resume_screenings.id` 查并校验 `job_code`；没有命中时再按 `job_code + candidate_name` 兜底匹配。
- 简历正文拼接规则在 `packResumeScreeningRow()`：如果 `resume_plaintext.trim().length >= 120`，只用 `resume_plaintext`；否则会把 `report_summary` 作为 `【AI 简历摘要】` 拼进去。
- 拼 prompt 前会对 JD 和简历做空白压缩：`.replace(/\s+/g, ' ')`；JD 最多取 12000 字符，简历最多取 20000 字符。
- 生成后的面试题会在创建/维护面试会话时写入 `interview_questions` 表，字段包括 `session_id`、`question_no`、`question_text`、`source`。
- `DASHSCOPE_API_KEY` 只用于请求头鉴权，不属于 prompt；不要把密钥写进文档或代码说明。

# AI 面试官模板与权限认知

- 后台菜单叫 `AI面试官`，页面组件在 `src/App.tsx` 的 `SystemInterviewPromptTemplatesView`。
- `AI面试官` 页面采用“列表 + 弹框”交互：列表展示模板；新增、编辑、复制都在弹框中完成。
- 新建模板时只在前端列表末尾追加一条未保存草稿，模板名称和 System Prompt 都为空；点击保存后才入库。
- 复制模板时在前端列表末尾追加一条未保存副本，内容来自被复制模板；点击保存后才入库。
- 弹框里的“恢复”只在编辑已有模板或复制草稿时出现，含义是恢复到“打开弹框那一刻”的内容；新建空白模板不显示恢复。
- 预设模板 `申朴面试官AI` 是数据库预设，不能删除；其默认 System Prompt 固化为 6 道题，不再使用 `{{total}}` 变量。
- 模板启用/删除/复制在列表行内操作；删除预设模板按钮必须禁用。
- 发起面试邀请时会选择 AI 面试官模板，服务端把模板 ID 写入 `interview_invitations.prompt_template_id`；生成面试题时按邀请绑定模板读取 System Prompt。
- `初面管理` 列表需要展示本场面试使用的 AI 面试官模板名称；历史无绑定模板的数据默认视为 `申朴面试官AI`。
- 模板权限不在模板页单独配置，统一由“角色管理”里的菜单权限控制：拥有 `sys-interview-prompt` / `AI面试官` 菜单的角色即可查看、发起选择、维护模板。
- 后台用户支持多角色，关系表是管理库 `user_roles`；旧字段 `users.role` 保留为主角色，用于兼容旧逻辑。
- 登录时会读取用户多个角色，并合并这些角色的 `roles.menu_keys` 菜单权限。
- 菜单管理支持 `目录`、`可见菜单`、`不可见菜单（数据权限）`；默认新增菜单应是可见菜单，不可见菜单用于数据权限配置。

# 后台列表交互认知

- `岗位分配` 页面在 `src/App.tsx` 的 `JobQueryView`，主要表格是“岗位列表”。
- 岗位列表里的 `交付负责人`、`招聘部门` 这类可能被截断的单元格，需要保留两行省略展示，同时用原生 `title` 在鼠标 hover 时显示完整内容。
- `招聘部门` 列展示的是根据岗位招聘人员匹配出的部门；hover 文案应直接给用户看完整招聘部门，不要展示内部解释字段。
- `项目状态` 徽标例如 `进行中` 必须不换行，避免窄列下拆成“进行 / 中”。
- 岗位编码例如 `JMP2373WX` 是岗位码，用于筛查、邀请、报告等关联；在后台列表里双击岗位码应复制到剪贴板。
- 双击复制岗位码后，需要在行内显示短暂的 `复制成功` 提示；鼠标样式保持默认，不要改成复制光标，也不要自动选中文字。
- 目前已处理 `岗位分配` 的岗位码双击复制成功提示；`初面管理` 的岗位编码也支持双击复制，但暂未加成功提示。

# 小程序面试测试助手认知

- 为了提高本地联调效率，小程序面试页可以启用“测试助手”，在当前题下提供 `低分 / 中等 / 高分` 三类自动回答按钮，避免每次都要真人口述。
- 测试助手只应作为本地开发能力，不应把大模型密钥写进客户端；客户端只调服务端接口，服务端继续复用现有 DashScope 配置。
- 当前测试回答接口是 `server/index.ts` 的 `POST /api/candidate/interview-test-answer`；前端调用封装在 `miniapp-candidate/src/services/interviewApi.ts`。
- 测试助手需要前后端双开关都开启才可用：客户端 `TARO_APP_INTERVIEW_TEST_HELPER=1`，服务端 `ENABLE_INTERVIEW_TEST_HELPER=1`。
- 生成回答时应基于当前题目、岗位、候选人上下文区分低/中/高质量，而不是写死模板文本，这样才能真实回归评分链路。

# 后台选择器与表单交互认知

- 后台中凡是**动态长列表**选择场景，都应优先使用统一 Picker 组件，而不是原生 `<select>`；短枚举项如状态、性别、是否、部门类型等可继续保留原生下拉。
- 当前通用选择器组件位于 `src/components/pickers.tsx`：
  - `SearchableSelect`：长列表单选，支持搜索、分页、自动定位当前值。
  - `TreeSelect`：树形单选，支持搜索、祖先链保留、层级回填。
  - `MultiSelectPanel`：长列表多选，支持搜索、分页、固定高度。
- 已经明确应接入可搜索组件的长列表场景包括但不限于：岗位、项目、部门、负责人、角色、目标岗位、职位筛选等；后续新增类似场景默认沿用这套组件。
- 树形选择器搜索命中子节点时，必须把它的上级链一起显示，不能只剩叶子节点，否则用户无法判断组织位置。
- 树形选择器收起后的已选值，需要保留层级可读性，优先展示完整路径，例如 `申朴信息 / 交付五部`，不要只显示最后一级。
- 树形选择器打开时，如果当前已有选中值，应基于**当前表单值**自动滚动到该节点附近，并尽量让目标项处于可视区域中部；如果用户在未保存前改选了别的节点，再次打开时应围绕新值定位。
- `MultiSelectPanel` 这类多选面板在搜索前后应保持内容区高度稳定，避免结果数变化导致弹窗整体抖动。
- 系统维护类编辑弹窗中，除“保存”外的关闭行为（右上角关闭、取消、点击遮罩）都应检测脏状态：有未保存修改时提示确认，未修改时直接关闭。
- 当前已按上述规则处理的维护弹窗包括：用户、部门、角色、菜单；后续新增同类弹窗默认也应复用这一交互约定。

# 部门树与排序认知

- 部门树不能依赖名称字典序排序；`交付一部 / 交付二部 / … / 交付十部` 这类名称若只按 `name ASC`，会出现 `交付十部` 排到 `交付二部` 前面的错误体验。
- 部门表需要持久化人工顺序字段 `sort_order`；服务端读取部门时应优先按 `level ASC, sort_order ASC, name ASC`，前端树形展开也应优先使用 `sort_order`。
- 管理库旧表若缺少 `sort_order`，服务启动时会自动补列；手工迁移文件为 `server/migration_depts_sort_order.sql`。
- 对历史没有排序值的同级部门，应先按自然顺序初始化；中文数字部门名称需要默认整理成 `一部 → 二部 → … → 十部`。
- 部门管理页需要提供“调整排序”模式，支持**同级部门拖拽排序**并立即持久化；拖拽排序不应跨父级。
- 部门排序一旦确定，部门管理列表、树形选择器、项目表单等所有依赖部门树的地方都应共享同一顺序。
